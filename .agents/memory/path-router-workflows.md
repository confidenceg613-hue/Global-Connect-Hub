---
name: Path-router vs combined workflow
description: How to decide between per-artifact workflows and a single combined workflow when artifact.toml files are present.
---

`artifact.toml` files live under `artifacts/*/.replit-artifact/` (a hidden directory) — a plain `find . -iname artifact.toml` can miss them if it excludes dotfiles/dirs; check that exact path before concluding they're absent.

Their presence does not by itself mean the public dev domain routes by path to each artifact's declared port — but once the platform has auto-registered multiple real artifacts (not just aspirational artifact.toml files sitting unused), it silently switches the public dev domain to a path-based router (pid1 proxies each `paths` entry to that service's declared `localPort`), independent of `.replit`'s `[[ports]]`/`[userenv.shared]`. This can happen after a project starts as a single combined workflow and only later gets registered as multiple artifacts.

**Why:** confirmed by direct evidence in one project: `curl` to the public `*.replit.dev` domain returned 502 on `/` but 200 on `/api/*`, while `curl localhost:5000` (where a combined `start-dev.sh` bound vite) returned 200 for both. `lsof` showed `pid1` itself holding connections to the app artifact's declared `localPort` (23863) — i.e. the platform's own supervisor is the one proxying by path, not a raw port-forward of `.replit`'s `[[ports]]`. `/api` worked only by coincidence because the combined script's api port (8080) happened to match the api artifact's declared `localPort`.

**How to apply:** if the public dev domain 502s on some paths while `curl localhost:<port>` succeeds and multiple real artifacts are registered (check the Artifacts list, not just `find`-ing artifact.toml files), suspect the path router is active and expects a real listener on each artifact's declared `localPort` — regardless of what `.replit`'s `[[ports]]`/global env say. Fix by making each artifact's own dev server bind its artifact.toml-declared port (e.g. a framework-level fallback default, or a per-artifact `.env`/config — not `.replit`'s `[userenv.shared]`, since that leaks into every workflow and can force the wrong port). A combined internal workflow (e.g. for port-5000 webview/internal screenshotting) can keep running in parallel on its own explicit ports without conflict, as long as it doesn't rely on the same global env the per-artifact processes need to diverge from. A per-artifact workflow left in FAILED state because it duplicates a port the combined workflow already serves correctly (e.g. two processes both wanting to be "the" api on 8080) is often benign — check via `curl` on the actual public domain path before spending effort reconciling it.

**Update:** in a case where the platform auto-registered real per-artifact workflows *after* a project had been running on a legacy combined `start-dev.sh`-style workflow, the two actively fought over the same port (both wanted 8080 for the API) and the combined workflow's embedded API process died/crashed on every restart once the per-artifact API workflow was also running — this was not benign, it broke the app outright. Fix was to fully `removeWorkflow` the legacy combined workflow (non-artifact-managed workflows can be removed; artifact-managed ones cannot) and let the per-artifact workflows be the sole run path, then update replit.md's "Running the app" section to match. Don't assume "benign FAILED state" — check whether the combined workflow's own process is crash-looping, not just whether the per-artifact one shows FAILED.
